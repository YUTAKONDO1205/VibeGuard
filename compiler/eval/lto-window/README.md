# eval/lto-window — the link-time observation window

The property observer sees one translation unit, at compile time, in the
frontend's process. Under LTO the optimiser runs a **second** time — at link
time, in a different process, over a merged module — and cross-translation-unit
disappearance happens there and nowhere else. A gauge on one stream does not
close a catchment budget.

This lane opens the observation window at the LTO backend, and it is as much
about what it refuses to measure as about what it measures.

The result it exists to produce, from a run on 2026-09-12:

```
xtu.full.compile         compile      OK                  ABSENT        -
xtu.full.link            lto-backend  OK                  LOST          DSEPass on handle
```

The same subject, the same control, the same optimisation level. At compile time
the wipe is not in `handle` at all — it is a call into another unit — so the
compile-time window has nothing to attribute. At link time the wipe appears in
`handle` (the inliner merged the helper in) and is then removed. The
`(pass, unit)` pair is `DSEPass` on `handle`, at stage `lto-backend`, checkpoint
`after-pass`. **That attribution is one the compile-time window cannot produce,
not because it was configured badly, but because the event is not in its
window.**

## Running it

```sh
REPO=$(cd "$(git rev-parse --show-toplevel)" && pwd)

# the plugin (see ../../pass-instrumentation/observer/README.md)
cmake -S "$REPO"/compiler/pass-instrumentation/observer -B ~/vg-build/pass-observer \
      -G Ninja -DLLVM_DIR=$(llvm-config-18 --cmakedir)
ninja -C ~/vg-build/pass-observer

bash "$REPO"/compiler/eval/lto-window/tools/make-lto-fixtures.sh
node "$REPO"/compiler/eval/lto-window/run-lto-window.mjs \
     --lab    ~/vg-lab/lto-window \
     --out    ~/vg-lab/lto-window/results \
     --plugin ~/vg-build/pass-observer/libPropertyObserver.so
```

`--out` inside the checkout is refused (exit 4). Nothing this lane writes is
tracked data; `scripts/check-packaging-invariants.mjs` refuses any path under
`compiler/` with a `fixtures` or `_results` segment, so the fixtures are
generated into the lab by a tracked script rather than committed.

Unit tests (pure functions only, no compiler):

```sh
node --test compiler/eval/lto-window/test/*.test.mjs     # 45 tests, 0 failures
```

## What each cell is

Two families, generated by `tools/make-lto-fixtures.sh`.

| family | subject | control | why |
|---|---|---|---|
| `xtu` | `handle` calls `secure_wipe` from another unit | `wipe_kept` wipes in place, read afterwards by a unit the link cannot see into | the loss exists only inside the link |
| `erasure` | `handle_request`, the shape `compiler/llvm-pass/tools/make-fixtures.sh` generates | `wipe_kept` in the same unit | the loss is complete before the link starts |

Both families carry the control **beside** the subject in the same measurement,
so "the wipe was removed" and "the observer stopped seeing wipes" cannot produce
the same number.

The `noinline` attributes on the four subject/control functions are a fixture
intervention and are declared as one in the generator's header. Measured without
them first: full LTO inlines both `handle` and `wipe_kept` into `main`, and the
linked executable defines neither (`nm` showed one `T main` and nothing else). A
`(pass, unit)` attribution needs a unit for its second half.

## The two guards, and why a lane without them would lie

`-Wl,--load-pass-plugin=` on a **non-LTO** link is silently ignored. Not a
warning, not a non-zero exit, not even a message when the named `.so` does not
exist (`../../docs/toolchain-probes.md` §2.4). Re-measured here on this lane's
own fixture:

```
non-LTO link with the plugin:  rc=0  stderr 0 bytes  no observer log written at all
non-LTO link with -Wl,--lto-debug-pass-manager:  rc=0   0 "Running pass" lines
full-LTO link, same flag (xtu):                  rc=0  176 "Running pass" lines
```

So a lane without guard 1 would run a **compile-time** pipeline, find an empty
log, and report it as a link-time observation with no findings.

**Guard 1 — this really is an LTO link.** Two independent halves:

1. every input the cell calls an LTO input starts with `BC \xC0\xDE`
   (measured: `4243c0de`), and every input the fixture deliberately keeps
   *outside* the merged module is **not** bitcode (measured: `io.o` is
   `7f454c46`). Both directions are checked — an opaque unit compiled `-flto` by
   mistake destroys the control just as thoroughly, and silently. The form each
   object was actually built as is read from the object
   (`llvm-bcanalyzer-18 -dump`: `FULL_LTO_GLOBALVAL_SUMMARY_BLOCK` vs
   `GLOBALVAL_SUMMARY_BLOCK`), not from the runner's word.
2. lld's own pass log, from `-Wl,--lto-debug-pass-manager`, is non-empty. That
   channel **needs no plugin**, which is the point: it cannot be fooled by the
   thing it is guarding.

**Guard 1 is shown firing on every run.** A guard that has never been observed to
refuse anything is not a guard, so the harness builds one extra link per family
whose objects were compiled *without* `-flto` while the link line still says
`-flto` — a real build shape, and the one the silent-ignore trap is dangerous in
— and requires it to be refused. From the run below:

```
negativeControl.xtu      fired: true   measurement: BROKEN_MEASUREMENT
  inputKinds [elf, elf, elf, elf]   lldRunningPassLines 0   observerEvRecords 0
  reasons: not-an-lto-link
           use.o is elf, not LLVM bitcode: this link is not an LTO link   (and 3 more)
negativeControl.erasure  fired: true   measurement: BROKEN_MEASUREMENT
  inputKinds [elf, elf, elf]        lldRunningPassLines 0   observerEvRecords 0
```

Both halves fire, independently: the inputs are ELF **and** the linker's log is
empty **and** the observer wrote nothing. If it ever does not fire, the harness
exits 2 — because at that point nothing in the lane distinguishes a link-time
reading from a compile-time one.

`--skip-negative-control` turns it off, and a run that turns it off **cannot
return 0**. Three things happen instead, and all three are mechanical
(`lib/record.mjs`, `test/record.test.mjs`):

```
negativeControl.xtu = { attempted: false, ran: false, skipped: true,
                        flag: "--skip-negative-control",
                        note: "not run in this run (--skip-negative-control): guard 1
                               was not shown to fire, so nothing in this run
                               distinguishes a link-time reading from a
                               compile-time one" }
skipped = { negativeControl: true, gcc: false, thinltoEvidence: false }
```

— the record says it, the printed table says it on its own line
(`negativeControl: SKIPPED (--skip-negative-control) -- …`), and the exit code is
3, not 0. `../../schema/interfaces.md` §7 reserves 0 for "everything asked for
was checked and nothing was found"; a run whose only demonstration that guard 1
can fire was switched off has not checked that, whatever its table says. The same
holds for `--skip-gcc` and `--skip-thinlto-evidence`.

This is a correction. Until 2026-09-12 this paragraph said the result "records
that it was skipped" and the code left the field as `{}` for both
`--skip-negative-control` and `--skip-gcc` — no flag, no note, no key anywhere in
the JSON — and the run exited 0 with a clean all-OK table. Only
`--skip-thinlto-evidence` was recorded, so the pattern existed and was not
applied.

**Guard 2 — the two readings of the pipeline agree.** The observer's own `PASS`
records and lld's log are taken from **one process**: the observed link carries
`-Wl,--load-pass-plugin` and `-Wl,--lto-debug-pass-manager` on the same command
line (`run-lto-window.mjs`, the third link in `linkWindowCell`), so the two
readings are of one pipeline run rather than of two links that ought to have
matched. They are compared both ways: as **sets** of pass ids and as
**ordered sequences** of `(pass, unit)`.

What refuses a cell is the SUBSET reading — a pass the observer reports that the
linker's own log does not contain is `BROKEN_MEASUREMENT`, not a result, because
an attribution taken from it names a pass that may not have been where it says.
The ordered reading is strictly stronger, it is the one that actually held on
every healthy cell here, and it does **not** gate: two readings that agree as
sets but not in order still name passes the linker really ran. A cell in that
state comes out `OK` with its attribution and carries
`notes: ["pass-readings-agree-as-a-set-but-not-in-order"]`, so the divergence is
on the record rather than only in a field nobody consults.

That distinction is a correction too: this paragraph used to describe the
refusal itself as the ordered comparison, while `lib/cell.mjs` gated on the
subset reading alone and `sequenceEqual: false` reached a cell with an empty
`reasons` array.

One asymmetry is structural and is excluded by name rather than by rounding:
LLVM's own `PrintPassInstrumentation` suppresses the pass-manager and
pass-adaptor shapes unless asked to be verbose, while the observer's callbacks
receive them like any other pass. On the `xtu` full-LTO cell:

```
observer before-pass callbacks       224
  of which PassManager/PassAdaptor    48
observer compared                    176
lld "Running pass:" lines            176
observerOnly []   lldOnly []   subset true   sequenceEqual true
excluded: FunctionToLoopPassAdaptor, ModuleToFunctionPassAdaptor,
          ModuleToPostOrderCGSCCPassAdaptor, PassManager<Function>,
          PassManager<LazyCallGraph::SCC, CGSCCAnalysisManager, LazyCallGraph &,
                      CGSCCUpdateResult &>
```

Every excluded id is a `PassManager` or a `PassAdaptor`. Nothing else is
excluded, and anything else the observer saw that lld did not would fail the
guard. The task asked for subset; equality is what actually held, and both are
reported because a run where they diverge is worth seeing rather than averaging.

Two ways of getting this comparison wrong were found by getting them wrong
first, and both are now unit-tested: splitting `Running pass: <id> on <unit>` at
the *first* space truncates ids containing spaces into passes lld never ran, and
not stripping lld's ` (7 instructions)` suffix reports 151 of 176 pairs as
mismatched on a run that was in exact agreement.

**Non-invasiveness.** `sha256` of the linked executable, stock versus observed:

```
4886407bdf1bf205b34029eac8960908421204e4e5f06a38c3c5f95256e8a19d  app.stock
4886407bdf1bf205b34029eac8960908421204e4e5f06a38c3c5f95256e8a19d  app.observed
```

Byte-identical, **while** the observer produced 388 `EV` records and 448 `PASS`
records. That pairing is the whole claim: a plugin that silently declined to
install also produces identical bytes, so byte-identity alone is not evidence of
anything. A cell with zero `EV` records is `BROKEN_MEASUREMENT`, never clean. The
lane also checks that `--lto-debug-pass-manager` on its own does not change the
bytes, so the guard-1 reading is taken from the same program as the result. If
the bytes ever differ with the plugin loaded, the harness exits 2 and says so;
it does not suppress it.

## ThinLTO is refused, and the refusal is measured

Under `-flto=thin` lld runs one backend per input module, each with its own
`PassBuilder`, and calls `llvmGetPassPluginInfo()` once per backend
(`../../docs/toolchain-probes.md` §2.2 measured `PLUGIN_LOADED=2` for two
modules). The observer is not built for that. Three lines, verified in the
sources for this lane:

```
compiler/pass-instrumentation/observer/PropertyObserver.cpp:55
    std::shared_ptr<Tracker> TheTracker;

compiler/pass-instrumentation/observer/PropertyObserver.cpp:153
    TheTracker = std::make_shared<Tracker>(std::move(Cfg));

compiler/pass-instrumentation/observer/History.cpp:56
    Out = std::make_unique<raw_fd_ostream>(Cfg.OutPath, EC, sys::fs::OF_Text);
```

Line 55 is a single process-global tracker. Line 153 is inside the
`[](PassBuilder &PB)` registration callback of `llvmGetPassPluginInfo`
(`PropertyObserver.cpp:141`–`:143`), so every backend **replaces** it. Line 56
opens `OBS_OUT` with `OF_Text` and no append flag, so every replacement
**truncates** the file the previous backend was writing. And `dispatch` reads the
global (`PropertyObserver.cpp:61`) while other backend threads are replacing it.

It is worse than "the last log wins", which is why the lane does not write that
sentence. Measured, on this lane's own fixtures, with lld's default thread pool:

| | `xtu` | `erasure` |
|---|---|---|
| observer log size | 147192 B | 237506 B |
| `HANDSHAKE` records | 78 | 93 |
| distinct module ids in them | 4 | 7 |
| torn lines | 25 | 77 |
| `intact` | false | false |

There are three input modules. The extra "module ids" are torn fragments:
`<woHANDSHAKE>`, `after`, `""`. Sample torn lines:

```
WholeProgramDevirtPass	wipe_kept	wipe_kept	ERASED
llvm.memset,memset,explicit_bzero,bzero,__memset_chk<use.oe>	declaration-only	handle	Rhandlehandlev	twip
```

A by-hand run of the same link, on an earlier version of this fixture, came back
as `data` rather than text — 190766 bytes containing 9 NUL bytes, the hole a
truncating reopen leaves behind — and one harness run of `xtu` **failed the link
outright**, with two backends' diagnostics spliced mid-word on stderr. The shape
varies run to run, which is what a race looks like.

Serialising the backends does not fix it, it only makes the loss quiet.
`--thinlto-jobs=1` produced a log that parses cleanly and contains one module's
history — `main.t.o`, `HANDSHAKE` once, both names `declaration-only`, 248 `PASS`
records — ending in `STATS 248 0 0 0 0 trace`: 248 passes seen, **zero** `EV`
records, **zero** units tracked. Between the last `PASS` record and that `STATS`
line sits a ~1.5 KB run of NUL bytes, so the file was written by more than one
writer at more than one offset (which writer put the `STATS` there is not
something this lane established). What a driver gets is a well-formed log about a
module that contains neither the subject nor the control, with nothing in it
saying that two other backends' histories were overwritten.

The dangerous part is that `<OBS_OUT>.summary.tsv` looked **fine** through all of
this. It carried a clean `SUMMARY handle … LOST` with `DSEPass` — a plausible,
well-formed attribution sitting beside a shredded main log. A lane that read only
the side file would have published it.

So: the ThinLTO link cell is `measurement = BROKEN_MEASUREMENT`,
`state = NOT_OBSERVED`, reason `plugin-multi-passbuilder`, and the fixture is
named in the record's `unobserved` list. The lane **runs** the ThinLTO link by
default, so that word is earned by this run's own evidence rather than asserted;
`--skip-thinlto-evidence` skips it and the cell then says `evidenceThisRun:
false`, which is a different claim and is written as one — in the cell, in
`thinLto.<family>.evidence` (`skipped: true` with the flag), in the printed
summary, and in an exit code that cannot be 0.

### Plugin change required to close the ThinLTO window (specification, not applied)

This lane does not modify `compiler/pass-instrumentation/observer/**`. What it
would take:

1. **A tracker per `PassBuilder`, not per process.** Replace the file-scope
   `std::shared_ptr<Tracker> TheTracker` (`PropertyObserver.cpp:55`) with one
   tracker owned by the registration callback and captured by the three lambdas
   it installs. Each `PassBuilder` then has its own, and `dispatch` takes it from
   its capture instead of reading a global that another thread is writing. The
   callbacks are already `PassInstrumentationCallbacks`-scoped, so the capture is
   the natural lifetime; nothing else in `dispatch` needs to change.
2. **A per-module log suffix.** `OBS_OUT` becomes a stem: each tracker writes
   `<OBS_OUT>.<sanitised module identifier>.tsv`, and the same suffix goes on the
   `.summary.tsv` side file. The module identifier is not known when
   `llvmGetPassPluginInfo` runs, so the file has to be opened lazily at the first
   module boundary (`Tracker::handshake` is already the first place a module id
   exists). Under full LTO this yields exactly one file, named `ld-temp.o`, so the
   full-LTO reading is unchanged apart from the name; a compatibility shim could
   keep the unsuffixed name when only one tracker was ever created.
3. **A manifest, so "one backend's log is missing" is detectable.** Each tracker
   appends one line naming its module to `<OBS_OUT>.modules` opened with
   `OF_Append`, under a mutex. A reader that finds N modules in the manifest and
   fewer than N logs knows a backend's history was lost, which is precisely the
   thing that is currently silent.
4. **Re-run the non-invasiveness checks.** `scripts/noninvasive.mjs` and the
   `native-plugins` CI job establish byte-identity for the compile-time path; any
   of the above changes the plugin's allocation and I/O behaviour and the claim
   has to be re-established, for ThinLTO as well as for the compile path. The
   negative control (`-opt-bisect-limit` must make the object differ) has to be
   re-run too, or "the bytes did not change" stops being information.
5. **A test with more than one module.** The observer's own suite never links, so
   nothing in it would catch a regression here. A ThinLTO link of two modules
   with a subject in each, asserting two logs and a two-line manifest, is the
   minimum.

Until that lands, ThinLTO pass attribution is `NOT_OBSERVED` here, and this lane
will keep saying so.

## gcc: `UNSUPPORTED`, and it is a different word

`UNSUPPORTED` in `../../schema/interfaces.md` §3.1 means *the toolchain refused
the invocation*. That is literally what happens, measured:

```
gcc-13 -O2 -flto ... -Wl,--load-pass-plugin=<so>
  rc=1  /usr/bin/ld: unrecognized option '--load-pass-plugin=<so>'
        /usr/bin/ld: use the --help option for usage information
        collect2: error: ld returned 1 exit status

gcc-13 -O2 -flto ... -fplugin=<libPropertyObserver.so>
  rc=1  lto1: error: cannot load plugin <so>: undefined symbol:
        _ZTVN4llvm18raw_string_ostreamE

gcc-13 -O2 -flto -fuse-ld=lld ... -Wl,--lto-debug-pass-manager
  rc=1  ld.lld: error: undefined symbol: main
```

The link-time channel this lane uses does not exist in gcc's toolchain: GNU ld
does not know the option, `lto1` will load a plugin but not an LLVM one, and
gcc's `-flto` objects (ELF with `.gnu.lto_*` sections, magic `7f454c46`, not
bitcode) are not something lld will optimise. `compiler/gcc-repair/README.md:302`
records the matching fact from the other side: WipePinGcc, loaded into an `-flto`
link, prints `refusing to install: loaded into the LTO back end, where this pass
does not run` — exactly twice, because `lto1` runs twice (`-fwpa`, `-fltrans`).

A **second and separate** fact: there is no gcc observer in this tree at all
(`compiler/pass-instrumentation/` holds `introduction`, `marker` and `observer`,
all LLVM `PassBuilder` plugins). That is a statement about this repository, not
about gcc, and it is kept in its own field rather than folded into the refusal.

What gcc *can* still answer, without any observer, is the differential — and this
lane records it, because otherwise the gcc row reads as though nothing happens on
gcc:

```
gcc-13, no LTO   subject: PRESENT in secure_wipe (0 store(s)/0B/1 memset call(s))
                 control: PRESENT in wipe_kept (2 store(s)/32B)      inlined: false
gcc-13, full LTO subject: ABSENT  in handle (0 store(s)/0B)
                 control: PRESENT in wipe_kept (2 store(s)/32B)      inlined: true
```

The same cross-unit disappearance, with the control holding in both builds. Only
the **attribution** is out of reach on gcc. Those readings come from
`../../gcc-repair/scripts/objdump_fill.py`, imported by `tools/read-wipe.py`
rather than copied — this tree has one disassembly oracle and this lane is not
going to be the second.

## The erasure family's control does not survive full LTO — reported, not hidden

`erasure.full.link` is `BROKEN_MEASUREMENT`, `controlHeld: false`, reason
`control-did-not-hold`, `the control ended LOST (first loss at SROAPass)`.

This is a real result about the fixture, and it is the sharpest thing the lane
found that was not asked for. The erasure family's control is only a control
while `consume` is opaque. Under full LTO nothing is opaque: `opaque.c` is
bitcode too, the link inlines both producer and consumer, SROA promotes the
32-byte buffer out of memory, and the wipe has no buffer left to wipe. The
disassembly of the stock full-LTO executable shows it plainly — `wipe_kept` is a
chain of `movzbl sink; mov %al,sink` and `handle_request` is 32
`xorb $imm,sink` and a `ret`: one `xorb` per byte of the fixture's 32-byte
buffer. Neither function has a stack buffer any more.

The harness records no disassembly, so this reading is by hand and the whole of
it is here:

```sh
cd fixtures/erasure && clang-18 -O2 -flto -c target.c opaque.c main.c
clang-18 -O2 -flto -fuse-ld=lld -o app.stock target.o opaque.o main.o
objdump -d app.stock --disassemble=handle_request | grep -cw xorb    # 32
objdump -d app.stock --disassemble=wipe_kept     | grep -cw movzbl   # 32
```

This sentence said `nineteen` until 2026-09-12. It was wrong by 13, it was the
one number in this file that no artifact could contradict, and it is now pinned
to the generator that emits the buffer by `test/record.test.mjs` rather than to
somebody's memory.

**A control has to be built for the window it is measured in.** `xtu`'s control
holds at link time only because `io.c` is deliberately kept out of the merged
module; `erasure`'s premise — "the producer and consumer are in another
translation unit" — is a premise that whole-program optimisation dissolves.

`controlHeld` is `false` here and not `null`. §3.1's subsection is explicit that
those are different answers, and that emitting `null` for a control that
demonstrably fell is what misdescribed 16 of 20 removals in the first real
envelope this tree scored.

## `OK` with `NOT_OBSERVED` is legal, and this lane used to refuse it

The pairing rule runs one way. A cell whose `measurement` is not `OK` has
`state = NOT_OBSERVED`. §3.1 then says, in bold, that **the converse does not
hold**: `state = NOT_OBSERVED` with `measurement = OK` is legal, "a third
situation that a symmetric rule would erase. The instrument ran, the record
hashes, the control was measured — and at this point there was no reading of
*this* property, because the subject was not in the translation unit, or the
observation point was never reached."

`lib/cell.mjs` threw on exactly that pair, with a message citing §3.1, and this
lane reported the throw as evidence that it enforces the spec mechanically. It
enforced the opposite of the spec for one of the three cases, inside the module
whose whole job is to keep "the instrument did not work" apart from "there was
nothing here to read". The case it mis-graded: log intact, EV records present,
the control measured and **held**, the subject name resolved, and no `SUMMARY`
row for the subject — graded `BROKEN_MEASUREMENT`, i.e. the lane blaming its own
observer for a fact about the program.

What it grades now, and the distinction is in the code rather than in this
paragraph (`lib/cell.mjs`, the `!subject` branch; `test/cell.test.mjs`):

| the instrument | the verdict |
|---|---|
| established — main log intact, evidence records counted, subject resolved, control measured and HELD — and still no row for the subject | `OK` / `NOT_OBSERVED`, reason `no-reading-of-the-subject-at-this-point` |
| anything less — integrity never established, no evidence records, subject never put to a module, or no control measured | `BROKEN_MEASUREMENT` / `NOT_OBSERVED`, reason `observer-recorded-no-history-for-the-subject` |

The first row is reachable rather than theoretical, and the comment that used to
sit there ("a resolved subject always gets a row") was the reason nobody looked:
the observer resolves a subject by **lineage**
(`lineageRoot(F.getName()) == OBS_TARGET_FN`, `History.cpp:119-129`) and records
each unit under its own, possibly mangled, **name** (`History.cpp:187`,
`U.Name = Key`), while this harness looks the row up by the fixture's plain name.
A subject that survives a link only as `handle.llvm.1041` resolves and has no row
under `handle`. Requiring a measured, held control before reading that as the
third situation is what keeps it from becoming a hiding place.

Neither word is a grade of the property, so no published number moves: no cell in
the 10-cell run below takes that branch. What moves is what an exclusion list
would have said happened — which is the whole of §3.1's argument, and the reason
a run with such a cell still exits 3 rather than 0: an instrument that worked and
read nothing has completed a run, not a check.

## Things this lane does not do, and things that surprised it

- **`finish()` never runs at link time.** lld exits without unwinding, so the
  tracker's destructor — the only caller of `Tracker::finish()` — does not fire,
  and the main log of a healthy full-LTO link has **no** `SUMMARY`, `HIST` or
  `STATS` at all (measured: `HANDSHAKE` 1, `SUBJECTRES` 2, `PASS` 448, `EV` 388,
  `UNIT` 2, and nothing else). The attribution survives only because
  `writeSummaryFile()` rewrites `<OBS_OUT>.summary.tsv` on every change. A reader
  that looked only at the main log would find no attribution in a run that
  produced one. This lane reads both — and, since 2026-09-12, guards both. The
  integrity guards (`logIntact`, `evidenceRecords`) were computed on the MAIN log
  only, so under full LTO the file that was guarded and the file the verdict came
  out of were two different files, and the unguarded one is the file this lane's
  own ThinLTO section calls the dangerous one. Each cell now carries
  `counts.summarySource` (`main` / `side` / `none`) plus the side file's own torn
  lines and NUL bytes, and a side file that is not intact is
  `BROKEN_MEASUREMENT` with reason `observer-summary-file-not-intact`.
- **What a cell publishes is what was measured.** The linker's per-kind line
  counts (`Running pass:`, `Running analysis:`, `Invalidating analysis:`, …) were
  computed on every run by `parseLldPassLog`, carried as far as the cell, and
  dropped when the cell was written into the results — so a figure quoted from a
  run could be reconciled against nothing. They are in every link cell's
  `guards.lldLineKinds` now, next to the `lldRunningPassLines` count that was
  always there.
- **One optimisation level, one target, one toolchain version.** `-O2`, x86-64
  ELF, clang/lld 18.1.3. `clang-15`…`clang-20` and `gcc-10`…`gcc-14` are
  installed on this machine and **were not used**: the plugin is built against
  one LLVM's headers and its `LLVM_PLUGIN_API_VERSION` will not load into another
  lld. Widening that axis means building the plugin per version, which this lane
  did not do and does not claim.
- **Two fixtures, one shape of loss.** A dead-store wipe. Nothing here says
  anything about the authz or configguard families at link time.
- **No corpus.** Ten cells, deliberately. The box is shared and a compile timeout
  is recorded as a failure, which would manufacture data.
- **The `erasure` link cell has no working control**, so this lane has measured
  nothing about `handle_request` at link time. It is `NOT_OBSERVED`, not
  `ABSENT`, even though the by-hand disassembly says the wipe is not there —
  because with a broken control, "the wipe is gone" and "the instrument is blind"
  are the same reading.
- **The ThinLTO corruption is nondeterministic.** Log size, `HANDSHAKE` count and
  torn-line count differ between runs, and one run failed the link. The *fact* of
  corruption reproduced every time; the numbers in the table above are from one
  run and should be read as one sample.
- **`--lto-emit-asm` / `--save-temps` are not used.** The verdict here comes from
  the observer's IR-level oracle, not from assembly. The assembly readings quoted
  above are context, taken by hand and by `objdump_fill.py`, not the verdict.

Three, none applied. Each is a request, and the lane works without them.

**1. `.github/workflows/ci.yml`** — the unit tests reach no runner. Every other

runner` step; this one is not, so `node --test` on it only happens by hand. The

```
          run_suite lto-window            compiler/eval/lto-window/test/*.test.mjs
```

These tests need no compiler and no plugin — they are pure functions over text
and bytes — so they belong in that job rather than in `native-plugins`.

**2. `compiler/schema/interfaces.md` §3.1, "The pairing rule"** — a third value of
`controlHeld` is unwritten. The subsection distinguishes `false` (measured and
fell) from `null` (never measured). It does not say what a cell carries when the
control **was measured and HELD** but the measurement is broken for some other
reason — a shredded log, a subject with no history. This lane writes `true`
there, because `null` would say nobody measured and somebody did. Suggested
addition to that subsection's table:

```
| `true` | the control **was measured and held**; the cell is excluded for some other reason | the cell's own `NOT_OBSERVED` |
```

If the answer is meant to be `null` regardless, say so there and this lane will
change; what it should not do is decide it privately.

**3. No `VG-ART` finding id was claimed.** `VG-ART-064`…`069` are free, but that

## Files

```

lib/lto-inputs.mjs        guard 1a — object magic and LTO form, from bytes

tools/read-wipe.py        the artifact reading, through gcc-repair's oracle
test/*.test.mjs           45 tests, no compiler required
```

Nothing under `compiler/` is written by a run: the fixtures, the work tree and
the results all live in the lab, and the harness refuses an `--out` inside the
checkout. Every record is scanned before it is written and a hit is exit 4 rather
than a warning — it fired with 17 hits on the first real run, which is how the
diagnostic-redaction call sites were found.

What the scan refuses is any **rooted, multi-segment path token**: a leading `/`
followed by at least two path segments, or a Windows drive letter
(`lib/record.mjs`). It used to be a seven-root whitelist —
`/(home|root|mnt|Users|tmp|var|usr)/` — which is a check for the roots this
machine happens to use, not for an absolute path: a lab under `/opt`, `/srv`,
`/data` or `/workspace` walked straight through the backstop this sentence calls
unconditional. The replacement was run over the lane's own 10-cell result before
being adopted (0 hits, the same as the pattern it replaced) and the shapes that
make a looser pattern tempting — `5/10`, `PassManager<…, LazyCallGraph &, …>`,
already-redacted `<ld>: unrecognized option` — are in `test/record.test.mjs`.
