# plugin-integrity

Answers one question about a compilation: **were the plugins it loaded ones the
policy authorises, and what pass pipeline actually ran?**

Everything below was measured on clang 18.1.3 (Ubuntu 24.04, WSL2). The raw
output is in `~/vg-lab/plugin-integrity/probe.md`, which is regenerated by
`~/vg-lab/plugin-integrity/mkprobe.sh`. Where this file states a fact about the
compiler, there is a command next to it that produces that fact. Nothing here
is inferred from documentation.

## Interface

```js
import { checkPlugins } from './integrity.mjs';

const { findings, pipeline, complete } = await checkPlugins({
  policy,   // parsed .vgpolicy.json; may be null or partial
  argv,     // the full compiler command line, argv[0] being the compiler
  env,      // the environment the compiler would see
  labDir,   // optional: where to drop raw capture artefacts. Never under compiler/.
});
```

`argv[0]` must be the compiler, because the pipeline is captured by invoking it
again (see [Pipeline capture](#pipeline-capture)). `env` is not decoration —
a plugin can be loaded with nothing in `argv` at all.

### Return value

| Field | Meaning |
|---|---|
| `findings` | Array of findings in the shape fixed by `compiler/schema/interfaces.md` §2. |
| `pipeline` | What was observed of the pass pipeline. See below. |
| `complete` | `false` if any check could not be carried out. Callers turn this into exit 3. |

```js
pipeline = {
  available: true,                    // false ⇒ no pipeline was observed
  method: 'print-pipeline-passes',
  reason: null,                       // why it is unavailable, when it is
  units: [ { source, passes, raw } ], // one entry per translation unit
  unitCount: 1,
  passes: [ … ],                      // convenience view of units[0]
  raw: 'fx/a.c\tannotation2metadata,…',
}
```

`complete` is the field that matters most. `findings: []` with
`complete: false` means *nothing was found and the looking was not finished* —
it never means clean. This is the distinction `interfaces.md` §7 exists to
protect, and it is the reason `checkPlugins` has a boolean rather than letting
an empty finding list speak for itself.

## Findings

| id | Raised when | Severity |
|---|---|---|
| `VG-PLG-001` | A plugin was loaded that could not be resolved or read, so its contents were never compared. Also forces `complete: false`. | `high` |
| `VG-PLG-002` | A plugin was loaded that the governing allowlist does not name. | `high` |
| `VG-PLG-003` | A plugin **is** named in the allowlist, but the bytes loaded hash to something the policy does not pin. | `critical` |
| `VG-PLG-004` | The observed pipeline differs from `toolchain.allowedPassPipeline`, in either direction. Also raised when that key is set and the pipeline could not be observed at all. | `medium` |

`VG-PLG-003` outranks `VG-PLG-002` deliberately. An unlisted plugin is an
unreviewed one; a listed plugin with different bytes is a reviewed name with
unreviewed contents behind it, which is the more specific and more deliberate
act.

`VG-PLG-004` is reported **once per differing pass, per translation unit**, with
`where.pass` naming the pass and `where.path` naming the unit it was observed
in. Summarising several differences into one finding would leave `where.pass`
either wrong or null, and `interfaces.md` §2 reserves null for "not applicable",
never "several".

## What counts as loading a plugin

Four spellings are recognised, and they were checked against the driver rather
than assumed:

| Spelling | Governed by | Notes |
|---|---|---|
| `-fpass-plugin=PATH` | `toolchain.allowedPassPlugins` | |
| `-Xclang -fpass-plugin=PATH` | `toolchain.allowedPassPlugins` | Measured working; injects identically. |
| `-fplugin=PATH` | `toolchain.allowedFrontendPlugins` | |
| `-Xclang -load [-Xclang] PATH` | `toolchain.allowedFrontendPlugins` | Both the paired and bare payload forms. |

`-fpass-plugin PATH` — space-separated — is **not** recognised, because the
driver rejects it:

```console
$ clang-18 -O1 -fpass-plugin /path/libMarkerPass.so -c a.c -o o.o
clang-18: error: unknown argument: '-fpass-plugin'
```

Treating it as a load would raise findings for a command line that cannot
compile in the first place.

`-fplugin-arg-<name>-<arg>` carries no path and is not treated as a load.

### The two lists are separate because the two mechanisms are

The policy schema keeps `allowedPassPlugins` and `allowedFrontendPlugins`
apart, and the reason is visible in the compiler's behaviour. Handing an LLVM
pass plugin to the Clang plugin slot is not an error — it exits 0, prints
nothing, and does nothing:

```console
$ clang-18 -O1 -fpass-plugin=libMarkerPass.so -c a.c -o pass.o   # 2 symbols injected
$ clang-18 -O1 -fplugin=libMarkerPass.so      -c a.c -o ast.o    # exit 0, 0 injected, no output
```

So a checker that knows one flag and not the other does not merely miss a case;
it reports a clean build for a command line it never examined. An allowlist
entry in the pass list does not excuse a load through the frontend slot, and
the finding text names which list governs the load.

### The check reads the command line, not the compiler's verdict

All three load spellings `dlopen` the shared object and run its constructors.
`-fpass-plugin=` does so and *then* rejects the file:

```console
$ clang-18 -O1 -fpass-plugin=./libCtor.so -c a.c -o /dev/null
error: unable to load plugin './libCtor.so': 'Plugin entry point not found …'
$ cat CTOR_RAN.txt
constructor executed
```

The constructor ran before the diagnostic was printed. Arbitrary code executed
inside the compiler process, and the compiler called it a failure. A check that
only inspected successfully-loaded plugins would have nothing to say about it.
So a load is a load from the moment the command line asks for one, and an
unreadable plugin is `VG-PLG-001` with `complete: false` rather than silence.

### A plugin can be loaded with nothing in `argv`

`CCC_OVERRIDE_OPTIONS` appends driver arguments from the environment:

```console
$ CCC_OVERRIDE_OPTIONS='+-fpass-plugin=./libMarkerPass.so' clang-18 -O1 -c a.c -o env.o
### CCC_OVERRIDE_OPTIONS: +-fpass-plugin=./libMarkerPass.so
### Adding argument -fpass-plugin=./libMarkerPass.so at end
$ nm env.o | grep marker
0000000000000020 T __marker_pass_present
0000000000000000 R __marker_pass_stamp
```

The recorded command line is clean; the object is not. `checkPlugins` therefore
parses this variable, attributes any load it finds to
`env:CCC_OVERRIDE_OPTIONS` in the finding text, and — because the variable can
also *rewrite* and *delete* arguments with `s/…/…/`, `x` and `X` operators that
this parser does not replay — sets `complete: false` when those operators are
present rather than claiming the argument list was fully understood.

## Pipeline capture

The pipeline is captured with `-mllvm -print-pipeline-passes`, which does work
through the driver and prints to **stdout**.

It is run as a **separate shadow invocation**, never added to the build being
checked, and this is not a stylistic preference:

```console
$ clang-18 -O1 -c a.c -o t1.o                                  # 1152 bytes
$ clang-18 -O1 -mllvm -print-pipeline-passes -c a.c -o t2.o
$ echo $?; stat -c %s t2.o
0
0
```

The flag short-circuits code generation. The compiler exits **0** and writes a
**zero-byte object**. Injecting it into a real build would empty every output
while every exit code stayed green — the exact failure mode this directory
exists to catch, produced by the tool meant to catch it.

The shadow command is built by dropping every `-o` and appending
`-o /dev/null`, and by compiling **one source file per run**. The second part
is load-bearing: a single shadow run over a multi-source invocation is rejected
outright —

```console
$ clang-18 -O1 -c a.c b.c -o /dev/null
clang-18: error: cannot specify -o when generating multiple output files
```

— and leaving the `-o` off instead would write zero-byte `a.o` and `b.o` into
the working directory, destroying the caller's outputs. (This is not
hypothetical: the probe script in `~/vg-lab/plugin-integrity/` does exactly
that in one section, which is how the hazard was noticed.)

Compiling one unit per run also gives real per-TU attribution, which the other
available flag cannot. `-Xclang -fdebug-pass-manager` — the only spelling the
driver accepts, output on stderr — never names the source file:

```console
$ clang-18 -O1 -Xclang -fdebug-pass-manager -c a.c b.c 2>two.err
$ grep -c -E 'a\.c|b\.c' two.err
0
```

Two TUs produce two concatenated pass streams whose only boundary is that the
pipeline restarts. Rather than splitting on that heuristic, the checker uses
per-source shadow runs, where the attribution is a fact about the invocation
instead of an inference about the text.

`-fdebug-pass-manager` is still worth knowing about for observers that must
watch a *real* build, because unlike the capture flag it leaves the object
byte-identical to an unflagged compile. `IrCheckpoints` and `PropertyObserver`
are the components that need that; this one does not.

### When capture fails

If any unit cannot be probed, `available` is `false` and `complete` is `false`,
even when other units succeeded. The units that did succeed are still returned
as evidence, and `reason` says how much of the invocation was covered:

```
the shadow invocation produced no pipeline for 1 of 2 source input(s): fx/bad.c (exit 1: …)
```

A build where the one interesting unit failed to probe must not be reported on
the strength of the boring ones.

## Record hygiene

`interfaces.md` §5 forbids absolute paths in records. Paths inside the working
tree are made relative; anything outside it is reduced to its basename, which
is also the only part the policy matches on. The rest of the path is dropped
rather than emitted. Every plugin finding names the file by basename and by
SHA-256, so the finding stays actionable without carrying machine-specific
paths.

## Positive control

A check that has never fired is indistinguishable from a function that returns
an empty array, so this one ships with something built to make it fire:
`compiler/pass-instrumentation/marker/`, target `MarkerPass`.

```sh
cmake -S compiler/pass-instrumentation/marker -B ~/vg-build/marker -G Ninja \
      -DLLVM_DIR=$(llvm-config-18 --cmakedir)
ninja -C ~/vg-build/marker            # → ~/vg-build/marker/libMarkerPass.so
```

It registers on the pipeline-start extension point, so **loading it is enough
to make it run** — which is the behaviour being defended against, and the
reason it does not merely register a named pass. It adds one function and one
global in a private section, and appends the global to `llvm.compiler.used` so
that later passes do not quietly delete the evidence.

```console
$ nm plain.o                       $ nm marked.o
0000000000000010 T addup           0000000000000020 T __marker_pass_present
                 U memset          0000000000000000 R __marker_pass_stamp
0000000000000000 T wipe            0000000000000010 T addup
                                                    U memset
                                   0000000000000000 T wipe
```

Two symbols and a `.marker_pass` section that no line of the translation unit
asks for; the object grows from 1152 to 1344 bytes. That is the
"unexplainable symbol" generator the `VG-INTRO-0NN` namespace will need, and
here it is the thing that proves this check is connected to reality.

The harness in `~/vg-lab/plugin-integrity/check.mjs` exercises it in both
directions — unlisted, correctly listed, and listed-but-tampered — and asserts
the quiet cases as hard as the loud ones.

## Known limits

Stated because an unstated limit reads as a covered case.

- **`CCC_OVERRIDE_OPTIONS` rewrite operators are not replayed.** Their presence
  makes the result incomplete rather than clean, but the checker cannot say
  what they would have produced.
- **Only `CCC_OVERRIDE_OPTIONS` is parsed.** Other paths into a compiler's
  argument list — response files, `CFLAGS` interpreted by a build system,
  wrapper scripts on `PATH` — are outside what this function is given.
- **The pipeline is captured from a second invocation, not from the build
  itself.** It is the pipeline that *would* run for that command line. A
  compiler that behaved differently between two identical invocations would
  defeat this, and nothing here detects that.
- **`allowedPassPipeline` must be written in the compiler's spelling.** The
  plugin's pass appears as `{anonymous}::MarkerPass`, not `MarkerPass`.
- **Dropping the caller's `-o` from the shadow command is defence in depth, not
  the mechanism.** clang takes the last `-o`, and the appended `-o /dev/null`
  is always last; a mutation that removes the dropping step is not caught by
  the harness, and that is understood rather than overlooked.
